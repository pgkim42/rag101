# C. 임베딩의 기초: 벡터로 뜻을 비교하기

> 임베딩은 텍스트를 「방향이 뜻을 나타내도록 학습된」 숫자 목록으로 바꾼다. 그러면 글자가 하나도 겹치지 않아도 뜻이 가까운 글을 찾을 수 있다. 대신 평균 내는 과정에서 순서, 부정, 숫자 같은 정보가 흐려진다.

표시 규칙: **[측정]** 은 이 저장소에서 돌려 얻은 값, **[예시]** 는 설명용으로 지어낸 값, **[기존 측정]** 은 앞선 장에 기록된 값이다.

## ① 학습 목표

- 스칼라·벡터·차원, 벡터의 크기와 방향을 2차원 숫자로 설명한다.
- 내적과 코사인 유사도를 손으로 계산하고, 둘의 순위가 왜 달라지는지 보인다.
- 정규화 뒤에는 내적이 곧 코사인이라는 것과, `retrieve.py`가 그 성질을 어디서 쓰는지 가리킨다.
- 문장이 벡터가 되는 과정을 토큰화 → 토큰 임베딩 → 문맥 표현 → 풀링 → 정규화로 나누고, 각 단계가 무엇을 하는지 실제 모델 값으로 보인다.
- 임베딩 모델과 생성 모델, 의미 유사성과 질문 적합성의 차이를 설명한다.
- 임베딩 검색이 실패하는 대표 상황을 측정값과 함께 든다.

## ② 선수 지식

- [B장](B-lexical.md): 토큰화, TF, BM25의 한계(같은 뜻·다른 글자).
- 피타고라스 정리(빗변² = 밑변² + 높이²)를 알면 벡터의 길이가 바로 이해된다.

## ③ 문제 상황

B장의 마지막 한계를 다시 보자 [측정, `labs/basics/vectors.py` 2부].

```text
같은 뜻, 다른 글자: 「햇빛을 전기로」와 「태양광 발전」
토큰 ['햇빛', '전기', '바꾼다'] / ['태양광', '발전'] → 겹치는 칸이 없으니 TF 벡터의 코사인은 0이다
```

실제 정답표에도 이런 질문이 있다. 「식물은 햇빛을 어떻게 에너지로 바꾸나?」에는 「광합성」이라는 낱말이 없다. 그런데 임베딩 검색은 광합성 글을 0.847로 1등에 올렸다 [기존 측정, 2장]. 어떻게 가능한가?

## ④ 가장 단순한 접근: 동의어 사전

「햇빛 = 태양광」, 「전기 = 발전」 같은 목록을 만들어 검색 전에 질문을 넓힌다(질의 확장).

## ⑤ 실패 사례

- **목록이 끝나지 않는다.** 「햇빛을 에너지로 바꾸다」 = 「광합성」은 낱말 대 낱말이 아니라 구절 대 낱말이다.
- **문맥을 모른다.** 「배 = 선박」이라고 적어 두면, 「배를 깎아 먹었다」도 선박이 된다.
- **언어를 넘지 못한다.** 한국어 질문으로 영어 문서를 찾으려면 언어쌍마다 사전이 필요하다.

필요한 건 낱말 목록이 아니라 **뜻을 비교할 수 있는 좌표**다. 비슷한 뜻은 가까운 좌표에, 다른 뜻은 먼 좌표에 놓는 방법이 있다면, 「가까운가」만 계산하면 된다.

## ⑥ 원리 설명

### 6.1 스칼라, 벡터, 차원

- **스칼라**는 숫자 하나다. 기온 23도, 점수 0.847.
- **벡터**는 순서 있는 숫자 목록이다. (3, 4)는 2차원 벡터, 임베딩 모델이 내는 숫자 384개는 384차원 벡터다.
- **차원**은 목록의 길이, 곧 독립된 축의 개수다. 2차원은 종이 위의 점, 3차원은 방 안의 점이다. 384차원은 그릴 수 없지만 계산 규칙은 2차원과 똑같다. 그래서 이 장은 2차원으로 원리를 익히고 384차원에 그대로 옮긴다.

### 6.2 크기와 방향

벡터를 원점에서 그 점까지의 화살표로 보면, 화살표에는 길이(크기)와 방향이 있다.

```text
길이 |a| = √(a₁² + a₂² + … + aₙ²)
```

(3, 4)의 길이는 √(9 + 16) = 5다. (5, 1)은 √26 = 5.099, (1, 0.9)는 √1.81 = 1.3454다.

임베딩에서는 **방향이 뜻을 담고, 길이는 대개 군더더기다.** (1, 0.9)와 (3, 2.7)은 같은 방향이고 길이만 3배다. 글이 길어서, 혹은 모델의 버릇 때문에 길이가 달라질 수 있는데, 그걸로 「더 관련 있다」고 판단하면 안 된다.

### 6.3 내적: 같은 자리끼리 곱해서 더한다

```text
a · b = a₁b₁ + a₂b₂ + … + aₙbₙ
```

질문 q = (1, 1), 문서 A = (1, 0.9), 문서 B = (5, 1)이라 하자 [예시].

```text
q · A = 1×1 + 1×0.9 = 1.9
q · B = 1×5 + 1×1   = 6.0
```

내적으로 줄 세우면 B가 1등이다. 그런데 그림을 그려 보면 q와 방향이 거의 같은 쪽은 A다. B는 옆으로 길게 뻗었을 뿐이다. 내적은 기하학적으로 `|a| × |b| × cos θ`(θ는 두 화살표 사이 각도)라서, **방향이 같은 정도와 길이를 섞어서** 잰다. B는 길이(5.099)로 이겼다.

### 6.4 코사인 유사도: 길이를 나눠 없앤다

```text
cos(a, b) = (a · b) / (|a| × |b|)
```

내적에서 두 길이를 나누면 cos θ만 남는다. 1이면 같은 방향, 0이면 직각(관계없음), −1이면 반대 방향이다.

```text
cos(q, A) = 1.9 / (1.4142 × 1.3454) = 1.9 / 1.9027 = 0.9986
cos(q, B) = 6.0 / (1.4142 × 5.0990) = 6.0 / 7.2111 = 0.8321
```

이번에는 A가 1등이다. 실습 출력 [측정, `vectors.py` 1부]:

```text
A=(1.0, 0.9): 길이 1.3454, q·A = 1.9000, cos(q,A) = 0.9986
B=(5.0, 1.0): 길이 5.0990, q·B = 6.0000, cos(q,B) = 0.8321
내적으로 줄 세우면 B가 1등, 코사인으로 줄 세우면 A가 1등이다.

같은 방향, 다른 길이: A와 3A
q·A = 1.9000, q·3A = 5.7000 / cos(q,A) = 0.9986, cos(q,3A) = 0.9986
```

### 6.5 정규화: 미리 길이를 1로 맞춰 두면

모든 벡터를 자기 길이로 나눠 길이 1(단위 벡터)로 만들어 두면, 코사인 식의 분모가 1 × 1이 된다. 그러면 **내적이 곧 코사인이다.**

```text
단위 q = (1/1.4142, 1/1.4142) = (0.7071, 0.7071)
단위 q · 단위 A = 0.9986  (= cos(q, A))
```

이게 실무에서 중요한 이유는 계산량이다. 문서 벡터를 미리 정규화해 저장해 두면, 질문이 올 때 「행렬 × 벡터」 곱셈 한 번으로 모든 문서와의 코사인이 나온다. 나눗셈이 필요 없다.

### 6.6 텍스트를 벡터로: 희소 벡터와 밀집 벡터

사실 B장의 TF도 벡터다. 어휘 전체를 축으로 두고, 칸마다 그 토큰이 나온 횟수를 적으면 된다 [측정, `vectors.py` 2부].

```text
차원 = 어휘 수 = 20. 칸 하나가 토큰 하나다.
D1 벡터에서 0이 아닌 칸: 8/20 — 대부분이 0이라 「희소(sparse)」 벡터라 부른다
cos(질문, D1) = 0.5222
cos(질문, D2) = 0.4444
```

| | 희소 벡터 (TF, BM25) | 밀집 벡터 (임베딩) |
| --- | --- | --- |
| 차원 | 어휘 수 (수만~수백만) | 모델이 정한 수 (여기서 384) |
| 칸의 뜻 | 칸 하나 = 토큰 하나. 사람이 읽을 수 있다 | 칸 하나에 정해진 뜻이 없다. 방향 전체가 뜻이다 |
| 0이 아닌 칸 | 몇 개뿐 | 거의 전부 |
| 값을 정하는 것 | 세기 | 학습 |
| 같은 뜻·다른 글자 | 겹치는 칸이 없어 0 | 가까울 수 있다 |

희소 벡터에서 「햇빛」 축과 「태양광」 축은 서로 직각이다. 둘이 가깝다는 정보가 들어갈 자리가 없다. 밀집 벡터는 축이 적은 대신, 학습으로 「햇빛」과 「태양광」을 비슷한 방향에 놓는다.

지어낸 3차원 예로 감을 잡자. 축이 (통신·보안, 빛·에너지, 돈·경제)라고 상상하고, 낱말마다 사람이 값을 정했다 [예시, `vectors.py` 3부].

```text
평균(햇빛, 전기) = [0.15, 0.9, 0.05]
평균(태양광, 발전) = [0.15, 0.8, 0.2]
cos(햇빛 전기, 태양광 발전) = 0.9825
cos(햇빛 전기, 통신 차단)   = 0.2212
```

글자가 하나도 안 겹쳐도 0.98이다. 실제 모델은 이 값을 사람이 아니라 학습이 정하고, 축이 384개이며, 축에 이름이 없다는 점만 다르다.

### 6.7 문장이 벡터가 되는 다섯 단계

`retrieve.py`가 쓰는 `paraphrase-multilingual-MiniLM-L12-v2`가 「식물은 햇빛을 어떻게 에너지로 바꾸나?」를 384개로 바꾸는 과정을 실제로 하나씩 밟는다 [측정, `labs/embedding_steps.py`]. 큰 그림은 [2장](02-embedding.md)에 있고, 여기서는 각 단계를 직접 계산해 `model.encode()`와 맞춰 본다.

**① 토큰화.** 문장을 모델 사전의 조각으로 자른다.

```text
① 자르기: 15조각 ['<s>', '▁식', '물', '은', '▁', '햇', '빛', '을', '▁어떻게', '▁에너지', '로', '▁바꾸', '나', '?', '</s>']
   조각 번호: [0, 34788, 8267, 697, 6, 221851, 131994, 413, 35078, 117254, 1083, 180559, 3497, 32, 2]
```

B장의 토큰화와 목적이 다르다. B장은 「겹치는 것을 세기 좋은 단위」를 찾았고, 여기는 「250,037개 사전으로 어떤 문장이든 표현할 수 있는 단위」가 목표다. 자주 나오는 덩어리(`▁어떻게`, `▁에너지`)는 통째로, 드문 것(`햇빛`)은 잘게(`햇`, `빛`) 자른다. 사전에 없는 글자가 거의 없으니 「모르는 낱말」 문제가 사라진다.

**② 토큰 임베딩(표에서 꺼내기).** 모델 안의 250,037행 × 384열 표에서 조각 번호의 행을 꺼낸다. 그다음 「몇 번째 자리인가」를 나타내는 위치 벡터를 더하고, 값의 크기를 고르게 맞춘다(LayerNorm).

```text
② 표에서 꺼내기: 표 크기 (250037, 384). '▁식' 행의 앞 4칸 = [0.0, -0.03, 0.007, -0.018]
   자리 번호 벡터를 더하고 정규화(LayerNorm)한 뒤 같은 조각의 앞 4칸 = [-0.09, -0.948, -0.143, -0.734]  → 이것이 1층에 들어가는 값
```

이 단계의 벡터는 **문맥을 모른다.** 표의 행은 조각마다 하나뿐이라, 「타는 배」의 `▁배`와 「먹는 배」의 `▁배`가 같은 행이다(아래 2부에서 코사인 1.000).

(정정: 2장과 `study.md`에는 `▁식`의 앞 네 칸이 `-0.044, 0.302, 0.120, 0.557`이라고 적혀 있었다. 이번에 다시 재 보니 표의 행 값과도, 위치 벡터와 LayerNorm을 거친 값과도 맞지 않았다. 2장은 위의 측정값으로 고쳤다.)

**③ 문맥 표현(어텐션 12층).** 각 조각이 같은 문장의 다른 조각을 얼마나 참고할지 정하고, 그 비율만큼 남의 정보를 섞는다. 이걸 12번 한다.

어텐션 한 번을 지어낸 숫자로 보자 [예시]. 조각 3개의 값 벡터가 v₁ = (1, 0), v₂ = (0, 1), v₃ = (1, 1)이고, 조각 1이 각 조각과 「얼마나 관련 있나」를 잰 점수가 (2, 1, 0)이라 하자. 점수를 비율로 바꾸는 소프트맥스(softmax)는 각 점수에 e^x를 취해 합으로 나눈다.

```text
e² = 7.389,  e¹ = 2.718,  e⁰ = 1    합 = 11.107
비율 = (7.389, 2.718, 1) / 11.107 = (0.665, 0.245, 0.090)
조각 1의 새 벡터 = 0.665 × (1,0) + 0.245 × (0,1) + 0.090 × (1,1) = (0.755, 0.335)
```

새 벡터는 「자기 자신 66.5% + 이웃 33.5%」의 가중 평균이다. 실제 모델에서는 관련 점수도 학습된 행렬로 계산하고, 이런 계산을 여러 갈래(헤드)로 동시에 한 뒤 합친다. 원리는 같다. 이렇게 12층을 지나면 조각마다 문맥이 묻은 384개가 된다.

```text
③ 12층을 지난 문맥 표현: (15, 384) (조각마다 384개)
```

같은 `▁배`도 문맥을 지나면 달라진다 [측정, `embedding_steps.py` 2부].

```text
  ② 표에서 꺼낸 「▁배」끼리 코사인: 1.000 (같은 행이니 1)
  ③ 문맥을 거친 「▁배」: 타는 배 vs 먹는 배 0.933, 타는 배 vs 아픈 배 0.930, 먹는 배 vs 아픈 배 0.939
```

1.000에서 0.93대로 갈라졌다. 다만 셋 사이 차이는 크지 않다. 이 작은 모델이 「배」의 세 뜻을 또렷하게 구분한다고 말하기는 어렵다. 문맥이 「묻는다」는 것까지가 이 측정이 보여 주는 사실이다.

**④ 풀링(평균).** 조각 15개의 384개를 자리별로 평균 내 384개 하나로 만든다. 이 모델의 풀링 방식이 평균이다(`[CLS]` 같은 첫 조각만 쓰는 모델도 있다). `<s>`, `</s>`도 평균에 들어간다.

```text
④ 평균 풀링: (384,), 앞 4칸 = [-0.196, 0.462, 0.102, 0.731], 길이 5.044
```

**⑤ 정규화.** 길이 5.044로 나눠 길이 1로 만든다.

```text
⑤ 길이를 1로: 길이 1.000
직접 밟은 결과와 model.encode()의 차이(가장 큰 칸): 1.86e-08
```

1.86e-08은 부동소수점 반올림 수준의 차이다. **다섯 단계를 손으로 밟은 결과가 라이브러리의 `encode()`와 같다.** 블랙박스였던 `encode()`가 이 다섯 단계라는 뜻이다.

정리하면 세 가지 「임베딩」을 구분해야 한다.

| 이름 | 무엇 | 문맥 | 단계 |
| --- | --- | --- | --- |
| 토큰 임베딩 | 표의 한 행 | 모른다 | ② |
| 문맥 토큰 표현 | 12층을 지난 조각별 벡터 | 안다 | ③ |
| 문장 임베딩 | 조각들을 평균 내고 정규화한 하나 | 문장 전체 | ④⑤ |

### 6.8 임베딩 모델과 생성 모델

| | 임베딩 모델 (인코더) | 생성 모델 (디코더) |
| --- | --- | --- |
| 출력 | 벡터 하나 | 다음 토큰의 확률 → 문장 |
| 어텐션 | 모든 조각이 앞뒤를 다 본다 | 각 조각은 앞쪽만 본다(뒤는 아직 안 썼으니까) |
| 여기서 | MiniLM, 384차원, 약 400MB | `gpt-6-luna`, API로 부른다 |
| 하는 일 | 검색용 좌표 만들기 | 붙여 준 글을 읽고 답 쓰기 |

둘 다 트랜스포머(어텐션을 쌓은 구조)지만, 학습 목표가 달라서 서로를 대신하지 못한다.

### 6.9 학습이 비슷한 문장을 가깝게 만드는 원리

표의 값과 어텐션의 행렬은 처음엔 무작위다. 학습은 이 숫자들을 조금씩 고쳐 「비슷한 문장 쌍은 코사인이 크게, 아닌 쌍은 작게」 만든다. 이를 대조 학습(contrastive learning)이라 부른다.

지어낸 숫자로 한 걸음만 보자 [예시]. 기준 문장 a와 그 바꿔 말한 문장 p(정답), 상관없는 문장 n₁, n₂가 있다. 지금 모델의 코사인이 다음과 같다.

```text
상황 1: cos(a,p)=0.8, cos(a,n₁)=0.3, cos(a,n₂)=0.1
상황 2: cos(a,p)=0.5, cos(a,n₁)=0.6, cos(a,n₂)=0.1
```

코사인에 20을 곱해(차이를 키우는 배율) 소프트맥스를 하면, 「여러 후보 중 정답 p를 고를 확률」이 나온다.

```text
상황 1: e^16 / (e^16 + e^6 + e^2) ≈ 0.99995  → 손실 −ln(0.99995) ≈ 0.00005
상황 2: e^10 / (e^10 + e^12 + e^2) ≈ 0.119    → 손실 −ln(0.119)   ≈ 2.13
```

상황 2는 정답보다 오답이 더 가까워 손실이 크다. 학습은 손실을 줄이는 방향(cos(a,p)는 올리고 cos(a,n₁)은 내리는 방향)으로 모든 숫자를 조금씩 고친다. 이걸 수백만 쌍에 반복하면, 비슷하게 쓰인 문장끼리 가까워지는 공간이 생긴다.

**이 모델은 어떻게 만들어졌나.** 모델 카드와 논문(Reimers & Gurevych, 2020, [arXiv:2004.09813](https://arxiv.org/abs/2004.09813))에 따르면, 먼저 영어 문장 임베딩 모델(선생)을 비슷한 뜻의 문장 쌍(paraphrase)으로 학습시켰다. 그다음 다국어 학생 모델이 영어 문장과 그 번역문 모두에서 선생과 같은 벡터를 내도록 학습했다(지식 증류). 그래서 한국어 질문과 영어 문서도 같은 공간에서 비교할 수 있다.

여기서 중요한 사실 하나: **이 모델은 「바꿔 말한 문장」끼리 가깝게 학습됐지, 「질문과 그 답」이 가깝게 학습된 것은 아니다.** 다음 절의 문제로 이어진다.

### 6.10 의미 유사성과 질문 적합성은 다르다

임베딩의 코사인은 「두 텍스트가 비슷한 이야기를 하는가」에 가깝다. RAG에 필요한 건 「이 문서가 이 질문에 답하는가」다. [측정, `embedding_steps.py` 3부]:

```text
  0.834  주제 같음, 묻는 것 다름 DNS 서버 주소는 어떻게 바꾸나? / DNS는 도메인 이름을 IP 주소로 바꾸는 시스템이다.
```

0.834는 이 질문에서 나올 수 있는 꽤 높은 값이다. 하지만 둘째 문장은 질문에 답하지 않는다. 질문과 답은 형태도 다르다(물음 대 서술). 그래서 질문과 문서에 서로 다른 표시(예: E5 모델의 `query: `와 `passage: ` 접두어)를 붙여 「질문 → 답」 관계로 학습한 비대칭 모델도 있다. 그래도 근본적으로 「답이 있는가」는 D장의 cross-encoder나 E장의 생성 단계가 더 잘 가린다.

### 6.11 Bi-encoder의 원리와 대가

질문과 문서를 **따로** 인코딩하고 벡터로만 비교하는 구조를 bi-encoder라 한다.

- **장점**: 문서 벡터를 미리 계산해 둘 수 있다(7장의 캐시). 질문이 오면 질문 하나만 인코딩하고 곱셈을 하면 된다. 질문 하나 인코딩에 5.66ms, 15편과 곱하고 정렬하는 데 0.01ms 미만이었다 [측정, `labs/score_fusion.py`].
- **대가**: 질문과 문서는 서로를 보지 못한 채 각자 384개로 요약된다. 질문의 핵심 낱말(「막나」)이 문장 평균에 묻히고, 문서의 수많은 낱말과 직접 맞대지 못한다. 3장의 「옆 주제를 집는」 오답이 여기서 나온다.

### 6.12 모델 입력 길이 제한

이 모델은 조각 128개까지만 읽는다. 넘는 부분은 **오류 없이 버려진다** [측정, `embedding_steps.py` 4부].

```text
  max_seq_length = 128. 앞의 글은 198조각(시작·끝 표시 포함).
  끝에 「결론: 이 글의 진짜 주제는 화산 폭발이다.」를 붙이기 전후 코사인: 1.000000
```

「진짜 주제는 화산 폭발」이라는 문장을 붙였는데도 임베딩이 한 자리도 바뀌지 않았다. 문서를 쪼개야 하는 가장 직접적인 이유다([5장](05-chunking.md)).

### 6.13 임베딩 검색이 실패하는 대표적인 상황

문장 쌍의 코사인 [측정, `embedding_steps.py` 3부]:

```text
  0.324  뜻 같음, 글자 다름    식물은 햇빛을 어떻게 에너지로 바꾸나? / 광합성의 원리
  0.717  부정             방화벽은 허가되지 않은 연결을 차단한다. / 방화벽은 허가되지 않은 연결을 차단하지 않는다.
  0.652  숫자             예금 금리는 연 3%다. / 예금 금리는 연 30%다.
  0.987  주어와 목적어 바꿈     고양이가 개를 쫓았다. / 개가 고양이를 쫓았다.
  0.834  주제 같음, 묻는 것 다름 DNS 서버 주소는 어떻게 바꾸나? / DNS는 도메인 이름을 IP 주소로 바꾸는 시스템이다.
  0.225  무관             식물은 햇빛을 어떻게 에너지로 바꾸나? / 김치찌개는 어떻게 끓이나?
```

| 상황 | 측정 | 읽는 법 |
| --- | --- | --- |
| 순서 바꿈 | 0.987 | 누가 누구를 쫓았는지가 반대인데 거의 같다. 평균은 순서를 거의 지운다 |
| 부정 | 0.717 | 뜻이 반대인데 꽤 가깝다. `vectors.py` 4부의 지어낸 예(0.9915)와 같은 원리다 |
| 숫자 | 0.652 | 3%와 30%가 다르다는 신호는 있지만 약하다 |
| 주제만 같음 | 0.834 | 답이 없는데 높다(6.10) |
| 짧은 바꿔 말하기 | 0.324 | 무관(0.225)보다는 높지만 생각보다 낮다. 「광합성의 원리」는 너무 짧아 단서가 적다. 광합성 **글 전체**와는 0.847이었다 |
| 길이 한도 | 1.000000 | 128조각 뒤는 안 보인다(6.12) |

**코사인의 절댓값은 혼자서 의미가 없다.** 0.717이 높은지 낮은지는 같은 모델, 같은 종류의 비교 안에서만 말할 수 있다. 검색은 「한 질문에 대한 문서들의 순서」만 쓰므로 그래도 동작한다. 하지만 「0.5 이상이면 관련 있음」 같은 고정 문턱은 모델이 바뀌면 다시 정해야 한다([6장](06-generation.md)의 문턱 실험).

## ⑦ 최소 구현

**무료, 표준 라이브러리만**

```bash
.venv/bin/python labs/basics/vectors.py
```

예상 결과는 위 6.4~6.6의 출력이고, 끝에 `모든 손 계산 검사를 통과했다.`가 나온다 [측정]. 5부는 저장 용량을 계산한다.

```text
         15편 × 384 × 4바이트 =        23,040바이트 ≈ 0.0 MiB
     10,000편 × 384 × 4바이트 =    15,360,000바이트 ≈ 14.6 MiB
  1,000,000편 × 384 × 4바이트 = 1,536,000,000바이트 ≈ 1,464.8 MiB
```

23,040바이트는 7장에 기록된 캐시 속 `vectors`의 크기와 같다.

**무료, 임베딩 모델 필요(.venv, 처음 약 400MB 내려받기)**

```bash
.venv/bin/python -m labs.embedding_steps
```

예상 결과는 위 6.7, 6.12, 6.13의 출력이다 [측정]. 실행할 때 Hugging Face 경고(`HF_TOKEN`)와 가중치 불러오기 진행 막대가 stderr에 나올 수 있다. 결과와 무관하다.

**결과 해석**: 1부의 차이 `1.86e-08`이 핵심이다. 1e-5보다 크면 직접 밟은 단계가 `encode()`와 다르다는 뜻이고 `assert`가 멈춘다. 3부의 숫자는 이 모델에서 잰 값이다. 다른 모델에서는 순서는 비슷해도 값은 다르다.

**실패 조건**: `RuntimeError: Passed CPU tensor to MPS op`가 나면 입력 텐서와 모델이 다른 장치(CPU 대 Apple GPU)에 있다는 뜻이다. 코드는 `.to(bert.device)`로 맞춰 두었다. 모델을 받지 못하면(네트워크) `OSError`가 난다.

## ⑧ 기존 프로젝트와 연결

| 개념 | 위치 |
| --- | --- |
| 모델 이름 | [`retrieve.py`](../retrieve.py)의 `MODEL_NAME` |
| ①~⑤ 전부 + 정규화 | `searcher.embedder.encode([question], normalize_embeddings=True)` |
| 정규화된 벡터끼리 내적 = 코사인 | `search()`의 `dense = searcher.doc_vectors @ query` |
| 문서 벡터를 미리 계산(bi-encoder의 장점) | `load_doc_vectors()`, [7장](07-cache.md) |
| 384차원을 2차원 지도로 | [`labs/embedding_map.py`](../labs/embedding_map.py), [2장](02-embedding.md) |

**이것을 제거하면?** `normalize_embeddings=True`를 빼면 `@`는 코사인이 아니라 내적이 된다. 6.3처럼 길이가 큰 벡터가 이긴다. 이 모델의 평균 풀링 벡터 길이는 문장마다 다르다(위 질문은 5.044).
