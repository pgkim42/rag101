# F. 평가와 검증: 숫자를 믿어도 되는가

> 지표는 정답표가 정한 질문에 대해서만 말해 준다. 질문이 적으면 숫자가 크게 흔들리고, 그 질문으로 설정을 고르면 숫자가 부풀려진다. 좋은 평가는 「무엇을 쟀고, 얼마나 흔들리며, 다시 재면 같은가」까지 적는다.

표시 규칙: **[측정]** 은 이 저장소에서 돌려 얻은 값, **[예시]** 는 설명용 값, **[기존 측정]** 은 앞선 장에 기록된 값이다.

[4장](04-evaluation.md)이 이 저장소의 세 검색 방식을 Hit@1, Recall@k, MRR로 잰 결과를 보여 준다. 이 장은 그 지표들을 정답이 여러 개인 경우와 nDCG로 넓히고, 「그 숫자를 얼마나 믿을 수 있나」를 다룬다.

## ① 학습 목표

- Ground Truth와 평가 데이터셋이 무엇이고, 이 저장소의 정답표가 무엇을 재고 무엇을 못 재는지 말한다.
- Hit@k, Precision@k, Recall@k, MRR, nDCG를 정답이 여러 개인 예제로 손 계산한다.
- 검색 평가와 생성 답변 평가가 무엇을 다르게 재는지 설명한다.
- 15문항에서 12/15와 14/15의 차이가 의미 있는지 구간과 부호 검정으로 판단한다.
- 하이퍼파라미터를 고른 데이터로 채점하면 왜 숫자가 부풀려지는지 시뮬레이션으로 보인다.
- 검색 품질과 응답 지연시간의 트레이드오프를 측정값으로 계산한다.
- 다시 돌려도 같은 결과가 나오는 실험 설계의 요소를 나열한다.

## ② 선수 지식

- [D장](D-retrieval.md): Recall과 Precision, 2단계 검색. [4장](04-evaluation.md): 이 저장소의 측정 결과.
- 확률을 「같은 일을 여러 번 했을 때 일어나는 비율」로 이해하면 충분하다.

## ③ 문제 상황

한국어 정답표로 쟀더니 다음과 같다 [기존 측정, 3·4장. 이번에 `labs/score_fusion.py`로 다시 재서 같은 값].

| 방식 | Hit@1 |
| --- | --- |
| dense | 12/15 |
| hybrid | 14/15 |

「hybrid가 dense보다 낫다」고 결론 내려도 될까? 영어에서는 rerank 14/15가 hybrid 15/15보다 낮았다. 「영어에서는 재순위화가 해롭다」고 해도 될까?

## ④ 가장 단순한 접근

정답 수를 세서 큰 쪽을 고른다.

## ⑤ 실패 사례

- **1등만 보면 정보를 버린다.** 정답이 2등이던 문항과 15등이던 문항이 둘 다 「틀림」이다. RAG는 k편을 붙이므로 2등은 대개 괜찮다(4장).
- **정답이 여러 개면 「맞음」이 애매하다.** 정답 문서가 두 편인 질문에서 하나만 찾으면 맞은 건가?
- **15문항은 적다.** 실력이 똑같은 두 방식도 15문항에서는 자주 2문항 넘게 차이가 난다(6.5).
- **고른 문제로 채점했다.** hybrid의 비중 0.7은 이 15문항을 보고 골랐다. 이 15문항에서 잘 나오는 게 당연하다(6.6).

## ⑥ 원리 설명

### 6.1 Ground Truth와 평가 데이터셋

Ground Truth(정답 기준)는 「이 질문에는 이 문서가 관련 있다」를 사람이 정해 둔 표다. 평가 데이터셋은 질문과 그 정답 기준의 묶음이다. 이 저장소에서는 [`data/answer_key.json`](../data/answer_key.json)이다.

```json
{ "id": 3, "file": "03-firewalls.md",
  "en": "What blocks unauthorized network traffic?",
  "ko": "허가되지 않은 네트워크 통신을 무엇이 막나?" }
```

이 정답표의 성격:

| 성격 | 결과 |
| --- | --- |
| 질문마다 정답 문서가 정확히 하나 | Recall@k가 Hit@k와 같다. 정답이 여럿인 경우를 못 잰다 |
| 문서 단위 정답 | 「그 문서의 어느 문장이 답인가」는 없다. 청크를 쪼개면 정답표를 다시 만들어야 한다(5장은 글자 위치로 대신 쟀다) |
| 15편 모두 주제가 다르게 골라졌다 | 쉬운 편이다. Recall@3이 모든 방식에서 1.000이라 방식 차이가 안 보인다(4장) |
| 질문이 15개 | 숫자가 크게 흔들린다(6.5) |
| 「관련 있음/없음」 두 단계 | 「완전한 답」과 「부분적인 답」을 구분하지 못한다(6.3의 nDCG) |
| 한국어 질문은 직접 옮긴 것 | 번역이 검색에 유리하거나 불리하게 작용했을 수 있다 |

### 6.2 지표를 손으로: 정답이 두 편인 질문

검색 결과가 위에서부터 `d3, d1, d5, d2, d4`이고, 정답은 `d1`(완전한 답)과 `d2`(부분적인 답)라 하자 [예시].

| 지표 | 정의 | 계산 |
| --- | --- | --- |
| Hit@k | 위 k편에 정답이 **하나라도** 있으면 1 | Hit@1 = 0 (d3은 정답 아님), Hit@2 = 1 |
| Precision@k | 위 k편 중 정답의 비율 | P@3 = 1/3 = 0.333 (d1만), P@5 = 2/5 = 0.4 |
| Recall@k | 정답 전체 중 위 k편에 든 비율 | R@3 = 1/2 = 0.5, R@5 = 2/2 = 1.0 |
| RR(역순위) | 첫 정답의 순위 r에 대해 1/r | 첫 정답 d1이 2등 → 1/2 = 0.5 |

정답이 하나면 Hit@k와 Recall@k가 같다. 정답이 둘 이상이면 다르다. Hit@k는 「하나라도 찾았나」, Recall@k는 「얼마나 다 찾았나」다. 여러 문서를 합쳐야 답이 나오는 질문(예: 「VPN과 방화벽의 차이는?」)에서는 Recall이 중요하다.

**MRR**은 질문마다 RR을 구해 평균 낸 것이다. 질문 세 개의 첫 정답 순위가 1, 3, 없음이면 [예시]:

```text
MRR = (1/1 + 1/3 + 0) / 3 = 1.3333 / 3 = 0.4444
```

### 6.3 nDCG: 순위와 등급을 함께

Hit, Recall, MRR은 「정답이냐 아니냐」 두 단계만 본다. nDCG(normalized Discounted Cumulative Gain)는 **얼마나 좋은 정답인지(등급)** 와 **얼마나 위에 있는지(순위)** 를 함께 본다.

```text
DCG@k  = Σ (2^등급 − 1) / log₂(순위 + 1)        (순위 1부터 k까지)
nDCG@k = DCG@k / (가장 이상적인 순서의 DCG@k)
```

| 부품 | 뜻 |
| --- | --- |
| 2^등급 − 1 | 이득(gain). 등급 0이면 0, 1이면 1, 2면 3. 좋은 정답일수록 크게 |
| log₂(순위 + 1) | 할인(discount). 1등 log₂2 = 1, 2등 log₂3 = 1.585, 4등 log₂5 = 2.322. 아래일수록 덜 쳐준다 |
| 이상적인 DCG로 나누기 | 0~1로 맞춘다. 정답이 많은 질문과 적은 질문을 비교할 수 있게 |

**등급 없이(정답 = 1점)** 계산해 보자. 정답이 2등과 4등에 있다.

```text
DCG  = 1/log₂3 + 1/log₂5 = 0.6309 + 0.4307 = 1.0616
이상 = 정답 두 개가 1, 2등 → 1/1 + 1/log₂3 = 1.6309
nDCG@5 = 1.0616 / 1.6309 = 0.6509
```

**등급을 넣으면(d1 = 2점, d2 = 1점).** d1(이득 3)이 2등, d2(이득 1)가 4등이다.

```text
DCG  = 3/log₂3 + 1/log₂5 = 1.8928 + 0.4307 = 2.3235
이상 = d1이 1등, d2가 2등 → 3/1 + 1/log₂3 = 3.6309
nDCG@5 = 2.3235 / 3.6309 = 0.6399
```

순서를 바꿔 d2를 2등, d1을 4등에 두면 [측정, `labs/basics/metrics.py` 1부]:

```text
Recall@5 1.000 (같음), RR 0.500 (같음), 등급 nDCG@5 0.5296 (낮아짐)
```

Recall과 RR은 차이를 못 느끼지만, nDCG는 「더 좋은 정답이 아래로 갔다」는 걸 잡는다. 대신 등급을 사람이 매겨야 해서 정답표를 만드는 비용이 커진다.

### 6.4 검색 평가와 생성 답변 평가

| | 검색 평가 | 생성 평가 |
| --- | --- | --- |
| 비교 대상 | 문서 id 목록 vs 정답 id | 답 문장 vs 정답 / 붙인 문서 |
| 판정 | 기계적(같은 id인가) | 뜻을 판단해야 한다 |
| 지표 | Hit@k, Recall@k, MRR, nDCG | 정확성, 근거성(groundedness), 질문 적합성, 거절의 적절성 |
| 비용 | 싸고 빠르다 | 사람, NLI 모델, LLM 판정이 필요하다 |
| 재현성 | 같은 입력이면 같다 | 생성 모델이 매번 다르게 답할 수 있다 |

생성 평가를 낱말 규칙으로 하면 쉽게 틀린다. `labs/unanswerable.py`는 답에 「모르」가 있으면 거절로 세는데, 「직각삼각형에서 **모르**는 변의 길이는 …」이라는 맞는 답을 거절로 셌다 [기존 측정, 6장]. 그래서 두 평가는 따로 하고, 따로 보고한다. 검색 지표가 좋아도 생성이 틀릴 수 있고(E장), 검색 지표가 나빠도 k를 넉넉히 주면 생성이 맞을 수 있다(6장).

### 6.5 작은 평가 데이터셋의 함정

**구간으로 보기.** 12/15 = 0.800이라는 숫자는 「이 15문항에서」의 값이다. 비슷한 질문을 무한히 많이 물었을 때의 진짜 정답률은 그 주변 어딘가다. 그 범위를 어림하는 방법 중 하나가 윌슨 구간이다(문항이 서로 독립이라는 가정이 깔려 있다) [측정, `metrics.py` 4부].

```text
   12/15  = 0.800 → 대략 0.548 ~ 0.930
   14/15  = 0.933 → 대략 0.702 ~ 0.988
   15/15  = 1.000 → 대략 0.796 ~ 1.000
  120/150 = 0.800 → 대략 0.729 ~ 0.856
  140/150 = 0.933 → 대략 0.882 ~ 0.963
```

- 12/15와 14/15의 구간이 크게 겹친다. 이 정보만으로는 둘의 진짜 실력이 다르다고 말하기 어렵다.
- 15/15도 「완벽」이 아니라 「진짜 정답률이 대략 80% 이상」이다.
- 같은 비율이라도 문항이 10배(150개)면 구간이 절반 이하로 좁아진다. 문항 수를 늘리는 게 가장 확실한 처방이다.

**같은 문항에서 갈린 것만 보기(부호 검정).** dense와 hybrid는 같은 15문항으로 쟀다. 둘 다 맞히거나 둘 다 틀린 문항은 둘을 구분해 주지 않는다. 결과가 갈린 문항만 보면 된다. 한국어에서는 Q3, Q9 두 문항이 갈렸고 둘 다 hybrid가 맞혔다 [기존 측정, 4장].

```text
두 방식이 사실 똑같이 좋다면, 갈린 문항 하나가 hybrid 쪽일 확률은 1/2
갈린 2문항이 모두 hybrid 쪽일 확률 = 1/2 × 1/2 = 0.25
```

똑같이 좋은 두 방식에서도 4번에 1번은 이런 결과가 나온다. 「hybrid가 낫다는 신호는 있지만, 우연으로도 흔히 나오는 정도」라고 말하는 게 정직하다. (보통 이 확률이 0.05보다 작아야 「우연이라 보기 어렵다」고 한다. 갈린 문항이 5개 이상이고 모두 한쪽이어야 0.5⁵ = 0.031로 그 선을 넘는다.)

**시뮬레이션으로 보기.** 진짜 정답률이 똑같이 80%인 두 방식을 15문항으로 2만 번 비교했다 [측정, `metrics.py` 5부, 난수 씨앗 고정].

```text
  20,000번 중 48.5%에서 2문항 이상 차이가 났다 (서로 독립된 문항 가정)
```

실력이 같아도 두 번에 한 번꼴로 「2문항 차이」가 난다. 12/15 대 14/15 같은 차이는 15문항에서 흔하다. (같은 문항으로 두 방식을 재면 두 방식의 결과가 서로 엮여 있어 차이가 이보다 덜 흔할 수 있다. 그래서 부호 검정처럼 갈린 문항만 보는 방법이 더 알맞다.)

### 6.6 하이퍼파라미터 튜닝과 과적합

하이퍼파라미터는 학습이 아니라 사람이 정하는 설정값이다. 이 저장소에는 `DENSE_WEIGHT = 0.7`, `RERANK_POOL = 5`, BM25의 `K1`, `B`, 청크 크기, `--k`가 있다.

**함정**: 설정 여러 개를 같은 평가 데이터로 재서 가장 좋은 걸 고르고, 그 점수를 보고하면 점수가 부풀려진다. 설정 10개가 모두 진짜 실력 80%인 상황을 시뮬레이션했다 [측정, `metrics.py` 6부].

```text
  개발용 15문항에서 1등 설정의 평균 점수: 0.943
  그 설정을 새 15문항(시험용)에서 잰 평균: 0.800
```

실제로는 모두 80%인데, 고른 설정의 점수는 94%로 보인다. 10개 중 그날 운이 가장 좋았던 것을 골랐기 때문이다. 새 문항에서 다시 재면 80%로 돌아온다. **고른다는 행위 자체가 점수를 올린다.**

이 저장소의 사례:

- hybrid 비중: 0.3, 0.5, 0.7, 0.9로 바꾸면 영어 Hit@1이 13, 14, 15, 14다 [측정, D장 6.7]. 0.7은 15문항을 보고 골랐다.
- BM25의 k1, b: 9가지 조합이 13~14를 오갔다 [측정, B장 6.9]. 이 중 「최고」를 골라 보고하면 같은 함정이다.
- rerank를 기본값으로 둔 근거 하나는 「후보 수를 3·5·10·15로 바꿔도 결과가 같았다」였다 [기존 측정, 3장]. 설정에 덜 민감한 방법은 과적합 위험이 작다.

**피하는 법**:

| 묶음 | 용도 | 규칙 |
| --- | --- | --- |
| 개발용(dev) | 설정 고르기, 오답 분석 | 마음껏 본다 |
| 시험용(test) | 마지막에 한 번 채점 | 설정을 고르는 동안 보지 않는다. 결과를 보고 다시 고르면 시험용이 개발용이 된다 |

질문이 적으면 교차 검증(질문을 여러 묶음으로 나눠 돌아가며 시험용으로 쓰기)을 쓰기도 한다. 15문항으로는 어느 쪽도 의미 있게 하기 어렵다. 이 저장소는 「과적합 위험이 있다」고 밝혀 두는 것으로 대신했다. 다음 단계는 더 큰 질문 모음이다(G장 4부).

### 6.7 검색 품질과 응답 지연시간

이 컴퓨터에서 질문 하나에 걸린 시간 [측정, `labs/score_fusion.py`, 질문 15개 평균].

```text
  질문 임베딩                5.66 ms
  15편 내적 + 정렬           0.00 ms
  BM25 점수               0.01 ms
  재순위화 5편              11.48 ms
  재순위화 15편             28.88 ms
```

여기에 생성 모델 호출이 더해지는데, 보통 수백 ms~수 초라 검색보다 훨씬 길다(네트워크와 답 길이에 따라 다르므로 이 저장소에서 따로 재지 않았다).

품질과 시간을 함께 보는 법:

| 방식 | ko Hit@1 | en Hit@1 | 질문당 검색 시간(어림) |
| --- | --- | --- | --- |
| dense | 12/15 | 12/15 | 약 6ms |
| hybrid | 14/15 | 15/15 | 약 6ms (BM25 0.01ms 추가) |
| rerank (후보 5) | 15/15 | 14/15 | 약 17ms |

Hit@1은 [기존 측정, 3장], 시간은 위 측정을 더한 어림이다. 이 표에서 hybrid는 dense 대비 시간을 거의 더하지 않고 품질을 올렸다. rerank는 시간을 약 3배 쓰고 한 언어에서만 나아졌다. **이 정도 차이(15문항 중 1문항)는 6.5에서 봤듯이 우연일 수 있다.** 그래서 지연 시간을 더 쓸 가치가 있는지는 더 큰 평가 데이터로 판단해야 한다.

지연 시간을 보고할 때는 평균만이 아니라 느린 쪽 꼬리(예: 100번 중 95번째로 느린 값, p95)도 본다. 사용자가 느끼는 건 가끔 오는 느린 응답이다.

### 6.8 재현 가능한 실험 설계

「다시 돌리면 같은 숫자가 나오는가」, 그리고 「다른 사람이 돌려도 같은가」를 위해 기록할 것들이다.

| 요소 | 이 저장소에서 |
| --- | --- |
| 데이터 버전 | `docs/`와 `data/answer_key.json`은 git으로 관리된다. 결과를 적을 때 커밋을 함께 적는다 |
| 모델 이름과 버전 | `MODEL_NAME`, `RERANK_MODEL`, `RAG_LLM_MODEL`. 같은 이름의 모델도 갱신될 수 있으니, 가능하면 리비전까지 |
| 파생물의 지문 | 임베딩 캐시는 모델 이름 + 문서 내용의 SHA-256으로 유효성을 확인한다(7장). 실험 결과에도 같은 생각을 쓸 수 있다 |
| 난수 씨앗 | `labs/basics/*.py`는 `random.Random(42)`처럼 씨앗을 고정해 몇 번을 돌려도 같다 |
| 생성 모델의 비결정성 | 같은 입력에도 답이 다르다(E장 6.5). 여러 번 돌려 분포를 보고, 몇 번 돌렸는지 적는다 |
| 환경 | 라이브러리 버전(`requirements.txt`), 하드웨어(지연 시간은 컴퓨터마다 다르다) |
| 원자료 | 지표만 남기지 말고 문항별 순위와 답 전문을 남긴다. 지표가 이상할 때 원인을 찾을 수 있다 |
| 측정과 예시의 구분 | 이 교재의 [측정] / [예시] / [기존 측정] 표시가 그것이다 |

## ⑦ 최소 구현

**무료, 표준 라이브러리만**

```bash
.venv/bin/python labs/basics/metrics.py
```

예상 결과: 위 6.2, 6.3, 6.5, 6.6의 출력과 끝 줄 `모든 손 계산 검사를 통과했다.` [측정]. 5~6부는 씨앗을 고정한 시뮬레이션이라 몇 번 돌려도 48.5%, 0.943, 0.800이 그대로 나온다.

**결과 해석**: 5~6부의 핵심은 숫자 자체보다 방향이다. 씨앗을 바꿔도 「실력이 같아도 자주 차이가 난다」와 「고른 설정의 점수는 부풀려진다」는 그대로다(연습 문제 6).

**실패 조건**: nDCG나 윌슨 구간의 손 계산 값과 다르면 `AssertionError`로 멈춘다. 공식을 바꿔 보는 실험을 하면 해당 assert부터 고치자.

**저장소의 실제 측정**: `.venv/bin/python -m labs.evaluate`가 세 방식의 Hit@1, Recall@3/5, MRR@5를 정답표로 잰다([4장](04-evaluation.md)).

## ⑨ 한계와 실무적 타협

| 이상 | 현실 |
| --- | --- |
| 수천 문항, 등급 매긴 정답표 | 처음에는 50~200문항이라도 실제 사용자 질문에서 모은다. 오답이 나올 때마다 문항으로 추가한다 |
| 사람이 모든 생성 답을 판정 | LLM 판정으로 대부분을 거르고, 표본만 사람이 확인해 판정기의 정확도를 잰다 |
| 개발용과 시험용을 엄격히 분리 | 작은 팀은 시험용을 「분기마다 한 번만 여는 금고」처럼 운영한다 |
| 모든 실험을 여러 번 | 검색처럼 결정적인 단계는 한 번, 생성 단계는 여러 번 |

데이터가 100배 늘면? 평가 비용도 는다. 검색 평가는 싸서 문항을 늘리기 쉽지만, 생성 평가는 문항마다 판정 비용이 든다. 그래서 검색 지표로 후보를 좁히고, 생성 평가는 마지막 몇 후보에만 쓴다.
