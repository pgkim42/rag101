# 7. 임베딩 캐시: 미리 계산해 두기

> 질문은 미리 알 수 없지만 글은 미리 안다. 글 임베딩은 한 번 계산해 저장해 두고, 글이나 모델이 바뀌었을 때만 다시 계산한다. 어려운 건 저장이 아니라 「언제 버릴지」다.

## 이 장에서 알게 되는 것

- 무엇을 미리 계산할 수 있고 무엇은 못 하는지
- 캐시를 언제 버려야 하는지, 그걸 어떻게 아는지 (지문)
- 캐시 파일이 깨졌거나 쓰다 멈췄을 때 어떻게 하는지
- 15편에서 실제로 얼마나 빨라졌는지

## 왜 필요한가

임베딩 검색은 질문과 글을 모두 숫자로 바꿔야 한다. 그런데 글 15편의 임베딩은 질문이 무엇이든 똑같다. 질문할 때마다 다시 계산할 이유가 없다. 글이 1만 편이 되면 이 계산이 몇 분씩 걸린다(아래 「빨라졌나」).

3장의 표가 이유를 하나 더 보여 준다. bi-encoder(임베딩)는 글 쪽을 미리 계산할 수 있고, cross-encoder(재순위화)는 못 한다. 미리 계산할 수 있다는 게 bi-encoder를 첫 단계에 쓰는 까닭이다.

## 원리

### 무엇을 저장하나

글 쪽만 `.cache/embeddings-ko.npz`(영어는 `embeddings-en.npz`)에 저장한다. 파일 안에는 두 가지가 있다.

| 이름 | 내용 | 크기 |
| --- | --- | --- |
| `vectors` | 15행 384열 숫자 표. 한 행이 글 한 편 | 15 × 384 × 4바이트 = 23,040바이트 |
| `fingerprint` | 이 숫자들이 어떤 글과 어떤 모델에서 나왔는지 적은 이름표 | 64글자 |

파일 전체는 23,818바이트였다. 질문은 여전히 물어볼 때마다 새로 계산한다.

`.cache/`는 `.gitignore`에 들어 있다. 언제든 다시 만들 수 있는 파생물이라 저장소에 올리지 않는다.

### 언제 버리나: 지문(fingerprint)

글을 고쳤는데 옛 숫자를 계속 쓰면, 검색은 고치기 전 글을 기준으로 줄을 세운다. **오류도 나지 않는다.** 조용히 틀리니 더 위험하다.

`fingerprint()`는 이렇게 이름표를 만든다.

```text
SHA-256( 모델 이름 + [파일 이름 + 제목과 본문] × 15편 )  →  64글자
```

해시는 입력이 한 글자만 달라도 완전히 다른 값이 나온다. 저장할 때 이름표를 같이 적고, 읽을 때 지금 글로 다시 구한 이름표와 맞춰 본다. 다르면 버리고 다시 계산한다.

| 이름표에 넣은 것 | 빠지면 생기는 일 |
| --- | --- |
| 제목과 본문 | 글을 고쳐도 옛 숫자로 검색한다 |
| 파일 이름 | 두 글의 순서가 바뀌어도 모른다. 1번 행이 2번 글을 가리킨다 |
| 모델 이름 | 모델을 바꿔도 옛 숫자를 쓴다. 다른 모델의 384개는 같은 길이여도 다른 공간의 좌표라, 섞으면 아무 뜻 없는 점수가 나온다 |

**파일 수정 시각으로 판단하지 않는 이유**: git으로 파일을 되돌리거나 새로 받으면 내용은 같아도 시각이 바뀐다. 모델이 바뀐 건 시각으로는 아예 알 수 없다. 내용을 직접 해시하는 쪽이 정확하고, 15편을 해시하는 시간은 느낄 수도 없다.

### 깨진 파일, 쓰다 멈춘 파일

- **깨진 파일**: 캐시는 없어도 되는 것이다. 읽다가 실패하면 다시 만들면 된다. 다만 잡는 오류는 「파일을 못 읽을 때」 나는 종류(`OSError`, `ValueError`, `KeyError`, `EOFError`, `BadZipFile`)로 좁혔다. 코드 실수까지 삼키면 버그가 숨는다.
- **쓰다 멈춘 파일**: `.partial`이라는 임시 파일에 다 쓴 다음 이름을 바꾼다. 쓰는 도중에 프로그램이 죽어도, 반쯤 쓴 파일이 캐시 자리에 남지 않는다. 같은 디스크 안에서 이름 바꾸기는 한 번에 일어나서, 다른 실행은 옛 파일이나 새 파일 중 하나만 본다.

## 이 저장소에서는

| 함수 | 하는 일 |
| --- | --- |
| `fingerprint(chunks)` | 모델 이름과 글 내용으로 이름표를 만든다 |
| `load_doc_vectors(chunks, embedder, lang)` | 캐시를 읽어 이름표를 맞춰 보고, 다르거나 못 읽으면 다시 계산해 저장한다 |
| `build_searcher(lang, method)` | 검색에 필요한 것(글, 모델, 글 임베딩, BM25)을 한 번만 준비한다 |

실행할 때 첫 줄 근처에 어느 쪽이었는지 나온다.

```text
글 임베딩 캐시 사용: .cache/embeddings-ko.npz
글 임베딩 계산 후 저장 (캐시 없음): .cache/embeddings-ko.npz
글 임베딩 계산 후 저장 (글이나 모델이 바뀜): .cache/embeddings-ko.npz
글 임베딩 계산 후 저장 (캐시를 읽을 수 없음): .cache/embeddings-ko.npz
```

## 직접 해 보기

아래 순서대로 해 보면 네 가지 경우를 다 볼 수 있다. 마지막에 글을 꼭 되돌리자.

```bash
rm -rf .cache
.venv/bin/python retrieve.py --check                       # 계산 후 저장 (캐시 없음)
.venv/bin/python retrieve.py --check                       # 캐시 사용
printf '\n덧붙인 문장.\n' >> docs/ko/01-photosynthesis.md
.venv/bin/python retrieve.py "광합성이란?"                  # 계산 후 저장 (글이나 모델이 바뀜)
git checkout -- docs/ko/01-photosynthesis.md
.venv/bin/python retrieve.py "광합성이란?"                  # 다시 계산 후 저장 (되돌린 것도 바뀐 것)
echo "this is not a zip" > .cache/embeddings-ko.npz
.venv/bin/python retrieve.py "광합성이란?"                  # 계산 후 저장 (캐시를 읽을 수 없음)
```

## 결과 읽기

| 한 일 | 출력 |
| --- | --- |
| 캐시 없이 `--check` | 계산 후 저장 (캐시 없음) |
| 한 번 더 `--check` | 캐시 사용. 채점 결과는 첫 번째와 한 줄도 다르지 않았다 |
| 광합성 글 끝에 문장 추가 | 계산 후 저장 (글이나 모델이 바뀜) |
| 그 파일을 git으로 되돌림 | 계산 후 저장 (글이나 모델이 바뀜) |
| 한 번 더 | 캐시 사용 |
| 캐시 파일을 아무 글자로 덮어씀 | 계산 후 저장 (캐시를 읽을 수 없음) |

되돌렸을 때도 다시 계산하는 게 맞다. 캐시는 마지막으로 본 한 가지 상태만 들고 있고, 그 상태는 「문장을 덧붙인 글」이었다.

### 빨라졌나

이 15편에서는 거의 아니다. `--check`가 3.2초에서 3.1초가 됐다. 실행 시간 대부분은 파이썬 라이브러리(torch, transformers)를 불러오는 데 들고, 글 15편을 숫자로 바꾸는 일은 0.2초 남짓이었다.

그래도 이 일은 글 수에 비례해 는다. 같은 속도로 어림하면 1,000편은 15초, 10,000편은 2분 반쯤이다. 질문마다 그만큼 기다릴 수는 없으니, 문서가 늘면 미리 계산은 선택이 아니다. 이 저장소는 그 구조를 15편으로 먼저 만들어 둔 것이다.

`--check`에는 구조적인 차이도 있다. 캐시를 넣기 전 코드는 문항마다 질문과 글 15편을 같이 계산했으니, 15문항이면 같은 글을 15번 계산했다. 지금은 처음 한 번뿐이고, 그 뒤로는 그마저도 안 한다.

## 다음에 오는 것: 벡터 데이터베이스

미리 계산해 둬도 비교는 여전히 「질문 하나 × 글 전부」다. 15편이면 곱셈 15번이라 아무것도 아니다. 글이 수백만 편이면 그 곱셈 자체가 느려진다. 그때는 가까운 것만 빨리 추리는 색인이 필요하고, 벡터 데이터베이스(FAISS, Chroma 같은 것)가 그 일을 한다. 저장해 둔 숫자 표가 그 색인의 재료다.

## 자주 하는 오해

- **「캐시는 저장만 하면 된다」**: 언제 버릴지가 핵심이다. 이름표 없이 저장만 하면, 글을 고친 뒤에도 옛 결과가 조용히 나온다.
- **「수정 시각으로 충분하다」**: git 작업 한 번에 틀리고, 모델 교체는 아예 못 잡는다.
- **「캐시가 깨지면 프로그램이 멈춰야 한다」**: 다시 만들 수 있는 것이면 다시 만들면 된다. 다만 「못 읽었다」 종류의 오류만 잡는다.

## 정리

- 글 임베딩은 질문과 상관없으니 미리 계산해 둔다. 질문 임베딩은 매번 새로 한다.
- 이름표 = 모델 이름 + 파일 이름 + 제목과 본문의 해시. 다르면 다시 계산한다.
- 임시 파일에 다 쓰고 이름을 바꿔, 반쯤 쓴 캐시를 남기지 않는다.
- 15편에서는 빨라진 게 거의 없다. 효과는 글 수에 비례해 커진다.

## 연습 문제

1. `fingerprint()`에서 모델 이름을 빼고, `retrieve.py`의 `MODEL_NAME`을 다른 임베딩 모델(예: `sentence-transformers/distiluse-base-multilingual-cased-v2`, 512개짜리)로 바꿔 돌려 보자. 무슨 일이 생기나? 384와 512처럼 길이가 다르면 오류가 나지만, 길이가 같은 모델이었다면?
2. 캐시를 읽는 데와 계산하는 데 각각 몇 초 걸리는지 `time.perf_counter()`로 재 보자.
3. 글이 수천 편이라면, 글 하나만 고쳤을 때 전부 다시 계산하지 않고 그 글만 다시 계산하려면 이름표를 어떻게 바꿔야 할까?
