# A. RAG 이전에 알아야 할 것

> 생성 모델이 쓸 수 있는 정보는 세 곳(학습 데이터, 파라미터, 컨텍스트)에 있다. RAG는 그중 컨텍스트를 질문마다 골라 채우는 방법이다. 고르려면 검색이 필요하고, 검색은 생각보다 어렵다.

표시 규칙: **[측정]** 은 이 저장소에서 명령을 돌려 얻은 값, **[예시]** 는 설명하려고 지어낸 값, **[기존 측정]** 은 앞선 장에 기록된 값이다.

## ① 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 「모델이 안다」는 말이 학습 데이터, 파라미터, 컨텍스트 중 어디를 가리키는지 구분해 설명한다.
- 같은 문제를 RAG로 풀지 Fine-tuning으로 풀지 근거를 들어 고른다.
- 순차 검색과 역색인(inverted index)을 직접 구현하고, 데이터가 100배 늘 때 무엇이 달라지는지 말한다.
- 코퍼스, 문서, 청크, 토큰을 이 저장소의 파일과 변수로 가리킨다.
- 「관련 있다」와 「답을 담고 있다」가 왜 다른지 예를 들어 설명한다.

## ② 선수 지식

- 백엔드 개발 경험(파일 읽기, 딕셔너리, 반복문). Python 문법은 실습 코드에서 필요한 만큼만 쓴다.
- 이 장은 다른 장에 기대지 않는다. 교재의 출발점이다.

## ③ 문제 상황

이 저장소에는 짧은 글 15편(`docs/ko/`)이 있다. 광합성, 방화벽, VPN, 인플레이션 같은 주제다. 다음 질문에 답하는 프로그램을 만들고 싶다.

```text
허가되지 않은 네트워크 통신을 무엇이 막나?
```

답은 `docs/ko/03-firewalls.md`에 있다. 「허용 기준에 맞지 않는 연결을 차단한다」는 문장이다. 생성 모델(LLM)이 이 문장을 근거로 「방화벽」이라고 답하게 하려면 무엇이 필요할까?

## ④ 가장 단순한 접근

세 가지를 떠올릴 수 있다.

1. **그냥 묻는다.** 생성 모델에게 질문만 보낸다.
2. **다 붙인다.** 글 15편을 전부 질문 앞에 붙여 보낸다.
3. **가르친다.** 글 15편으로 모델을 추가 학습(Fine-tuning)시킨다.

## ⑤ 실패 사례

이 질문은 상식이라 1번도 아마 맞힐 것이다. 그래서 질문을 바꿔 보자. 「우리 회사 VPN 접속 서버 주소는?」, 「어제 바뀐 휴가 규정은?」.

- **그냥 묻기**는 모델이 본 적 없는 정보 앞에서 실패한다. 더 나쁜 경우, 그럴듯한 답을 지어낸다. 맞혔다 해도 어디서 온 답인지 확인할 길이 없다.
- **다 붙이기**는 15편이면 된다. 15편은 2,827글자이고, 임베딩 모델 토크나이저로 1,562조각이다 [기존 측정, 5장]. 그런데 문서가 10만 편이면 어림잡아 1,000만 조각이다(1편 ≈ 104조각 × 100,000 = 10,400,000 [예시 계산]). 모델이 한 번에 읽는 길이(컨텍스트 창)를 넘고, 넘지 않더라도 요청마다 그만큼의 비용과 시간이 든다. 상관없는 글이 많을수록 모델이 엉뚱한 글을 근거로 집을 기회도 는다.
- **가르치기**는 사실 하나를 바꿀 때마다 다시 학습해야 한다. 학습이 끝나도 그 사실을 정확히 기억한다는 보장이 없고, 답이 어느 문서에서 왔는지도 알 수 없다.

## ⑥ 원리 설명

### 6.1 모델이 정보를 얻는 세 곳

| | 학습 데이터 | 파라미터 | 컨텍스트 |
| --- | --- | --- | --- |
| 무엇 | 모델을 만들 때 읽힌 글 전체 | 학습 결과로 정해진 숫자들(가중치) | 이번 요청에 함께 보낸 글 |
| 비유 | 학창 시절 읽은 책 | 머릿속 기억 | 시험장에 들고 들어간 참고 자료 |
| 언제 정해지나 | 학습 전 | 학습이 끝날 때 | 요청할 때마다 |
| 바꾸려면 | 다시 학습 | 다시 학습(또는 Fine-tuning) | 다음 요청에 다른 글을 넣으면 끝 |
| 출처 확인 | 불가능에 가깝다 | 불가능에 가깝다 | 넣은 글이니 가능 |
| 크기 제한 | 거의 없음 | 모델 크기 | 컨텍스트 창 |

학습 데이터는 모델에 「저장」되지 않는다. 학습은 데이터를 보고 파라미터를 조정하는 과정이고, 끝나면 남는 건 파라미터뿐이다. 그래서 모델의 지식은 압축되고 뭉개진 기억에 가깝다. 정확한 숫자, 드문 고유명사, 학습 이후의 사건에 약한 이유다.

**RAG는 세 번째 칸을 이용한다.** 질문마다 관련 글을 골라 컨텍스트에 넣는다. 그러면 파라미터를 건드리지 않고도 새 정보를 쓰게 할 수 있고, 어떤 글을 넣었는지 알기 때문에 근거를 보여 줄 수 있다.

### 6.2 RAG와 Fine-tuning

| | RAG | Fine-tuning |
| --- | --- | --- |
| 바꾸는 것 | 컨텍스트(입력) | 파라미터 |
| 새 사실 반영 | 문서를 고치면 다음 질문부터 | 다시 학습 |
| 근거 제시 | 넣은 문서를 보여 줄 수 있다 | 어렵다 |
| 잘하는 것 | 자주 바뀌는 사실, 출처가 필요한 답 | 말투, 형식, 특정 작업 방식 익히기 |
| 실패하는 곳 | 검색이 엉뚱한 글을 고를 때 | 학습한 사실을 부정확하게 떠올릴 때 |

둘은 경쟁 관계가 아니다. 「답의 형식을 우리 회사 양식에 맞춘다」는 Fine-tuning이 맞고, 「최신 규정으로 답한다」는 RAG가 맞다. 함께 쓰기도 한다. 이 저장소는 모델을 하나도 학습시키지 않는다. 받은 임베딩 모델과 재순위화 모델, API로 부르는 생성 모델을 그대로 쓴다.

### 6.3 검색 엔진은 「미리」와 「나중」으로 나뉜다

검색의 핵심 아이디어는 일을 두 시점으로 나누는 것이다.

- **미리(색인, indexing)**: 문서가 들어올 때 한 번, 검색하기 쉬운 구조를 만든다.
- **나중(질의, query)**: 질문이 올 때마다, 그 구조를 이용해 빨리 후보를 찾는다.

**순차 검색**은 「미리」가 없다. 질문이 올 때마다 문서를 처음부터 끝까지 하나씩 연다. 문서 수를 N, 문서 평균 길이를 L이라 하면 질문 하나에 대략 N × L에 비례하는 일을 한다.

**역색인**은 책 뒤의 찾아보기다. 「토큰 → 그 토큰이 나오는 문서 목록」을 미리 만들어 둔다. 이 목록을 포스팅 목록(postings)이라 부른다.

```text
문서                              역색인 (토큰 → [문서(그 문서에서 나온 횟수)])
03: 방화벽은 ... 통신을 ...        방화 → [03(3)]
15: VPN은 ... 통신 내용을 ...      통신 → [03(1), 15(1)]
                                   는다 → [01(1), 09(1), 13(1), 15(1)]
```

질문이 오면 질문 토큰의 포스팅 목록만 꺼낸다. 질문 토큰이 하나도 없는 문서는 아예 보지 않는다. 위 표의 숫자는 실제 15편으로 만든 역색인이다 [측정, 아래 ⑦].

역색인의 비용은 질문 토큰이 얼마나 흔한지에 달려 있다. 드문 토큰의 목록은 짧고, 흔한 토큰의 목록은 길다. 모든 문서에 있는 토큰은 결국 문서 전체를 읽게 만든다. 그런 토큰은 어느 문서인지 가려 주지도 못한다. 이 관찰이 B장의 IDF로 이어진다.

### 6.4 코퍼스, 문서, 청크, 토큰

| 말 | 뜻 | 이 저장소에서 |
| --- | --- | --- |
| 코퍼스 | 검색 대상 문서 전체 | `docs/ko/`의 15편 (`--lang en`이면 `docs/en/`) |
| 문서 | 사람이 쓴 한 단위 | `.md` 파일 하나 |
| 청크(조각) | 검색과 임베딩의 단위. 문서를 쪼갠 것 | 지금은 문서 하나 = 청크 하나. `retrieve.py`의 `load_chunks()`가 만드는 `dict` 하나 |
| 토큰 | 기계가 텍스트를 자르는 최소 단위 | **누가 자르느냐에 따라 다르다.** BM25는 두 글자 조각(`bm25.py`의 `tokenize()`), 임베딩 모델은 자기 토크나이저 조각(`▁식`, `물`, `은`) |

마지막 줄이 자주 헷갈린다. 「토큰 128개 한도」라고 할 때의 토큰은 임베딩 모델의 토큰이고, BM25가 세는 토큰과는 다른 것이다. 같은 글이라도 BM25 토큰 수와 모델 토큰 수가 다르다.

### 6.5 「관련성이 높다」는 무슨 뜻인가

정보 검색에서 관련성(relevance)은 **문서가 질문한 사람의 정보 요구를 채우는 정도**이고, 최종 판단은 사람이 한다. 수식이 먼저 있는 개념이 아니다. 검색 알고리즘의 점수는 이 판단을 흉내 내려는 근사값일 뿐이다.

관련성에는 층이 있다.

| 층 | 예: 「DNS 서버 주소는 어떻게 바꾸나?」 |
| --- | --- |
| 주제가 같다 | DNS 글. 주제는 정확히 같다 |
| 답을 담고 있다 | 15편 중 없다. DNS 글은 DNS가 무엇인지만 설명한다 |
| 그 문서만으로 답할 수 있다 | 없다 |

이 질문에서 DNS 글은 재순위화 점수 2.272로, 답이 있는 질문들의 1등 점수보다도 높았다 [기존 측정, 6장]. 검색 점수는 주로 첫째 층을 잰다. RAG에 필요한 건 둘째, 셋째 층이다. 이 간격이 E장의 주제다.

### 6.6 「검색 결과가 정답을 포함한다」는 무슨 뜻인가

평가할 때 쉽게 쓰는 말이지만, 세 가지가 다르다.

1. **정답 문서가 결과에 있다.** `data/answer_key.json`의 `file`이 위 k편 안에 있다. 이 저장소의 지표(F장)가 재는 것이다.
2. **정답 문장이 실제로 모델에게 전달됐다.** 문서가 잘리면 아니다. 밀물과 썰물 글은 임베딩 모델 한도(128조각)를 넘어 끝의 「번씩 겪는다.」가 임베딩에서 빠진다 [기존 측정, 2장]. 생성 모델에게는 전부 전달되지만, 청크를 잘게 쪼갰다면 답 문장이 다른 청크로 넘어갔을 수도 있다.
3. **그 문장만으로 답이 나온다.** 「그래서 대부분의 해안은 하루에 두 번 이를 겪는다」만 받으면 「이를」이 무엇인지 모른다(5장).

### 6.7 정확한 검색이 왜 어려운가

| 어려움 | 예 |
| --- | --- |
| 어휘 불일치 | 질문은 「햇빛을 에너지로」, 글은 「광합성」. 같은 글자가 없다 |
| 다의성 | 「배」는 타는 배, 먹는 배, 아픈 배 |
| 질문이 짧다 | 「Why does it rain?」은 단어 네 개. 단서가 적다 |
| 주제가 가까운 문서 | 방화벽과 VPN은 둘 다 네트워크 보안이다. 둘 중 무엇이 「막는가」를 가려야 한다 |
| 답이 없는 질문 | 검색은 늘 「가장 가까운」 문서를 낸다. 아무리 멀어도 |
| 규모 | 문서가 많아질수록 비슷한 오답 후보가 늘고, 다 비교할 시간이 없다 |

B~D장은 이 표의 줄을 하나씩 다룬다.

## ⑦ 최소 구현

표준 라이브러리만 쓰는 실습이다. 무료이고 생성 모델 키가 필요 없다.

```bash
.venv/bin/python labs/basics/inverted_index.py
```

(`.venv`가 없어도 `python3 labs/basics/inverted_index.py`로 돌아간다. Python 3.10 이상.)

**예상 결과 [측정]**

```text
=== 1부. 실제 한국어 15편 ===
글 15편, 서로 다른 토큰 903개, 포스팅 1151개
  '방화'   →  1편: 03(tf=3)
  '통신'   →  2편: 03(tf=1), 15(tf=1)
  '는다'   →  4편: 01(tf=1), 09(tf=1), 13(tf=1), 15(tf=1)
질문 토큰 12개. 순차 검색은 글 15편을 열었고, 역색인은 포스팅 9개를 읽었다.
질문 토큰이 하나라도 있는 글: 2편 — 이것은 「후보」일 뿐 순위가 아니다

=== 2부. 가짜 코퍼스로 크기를 키우면 (글당 30토큰, 어휘 20,000개) ===
      글 수     순차: 연 글       역색인: 읽은 포스팅      순차 시간      역색인 시간
      150         150               0.6     0.06ms     0.000ms
    1,500       1,500               7.3     0.82ms     0.002ms
   15,000      15,000              67.7     8.84ms     0.009ms
  150,000     150,000             696.7    89.90ms     0.103ms

가장 흔한 두 단어(w0, w1)로 물으면 15,000편 중 포스팅 25,880개를 읽는다.
```

시간 열은 이 컴퓨터에서 잰 참고값이라 실행할 때마다 조금씩 다르다. 「연 글」과 「읽은 포스팅」 열은 난수 씨앗을 고정해서 늘 같다.

**결과 해석**

- 1부: 질문 「허가되지 않은 네트워크 통신을 무엇이 막나?」의 두 글자 조각 12개 중, 15편 어디에든 있는 조각의 포스팅을 다 합쳐도 9개였다. 순차 검색은 15편을 다 열었다. 두 방법이 찾은 후보(2편: 방화벽, VPN)는 같다. **역색인은 결과를 바꾸지 않고 일의 양만 줄인다.**
- 2부: 문서가 100배(1,500 → 150,000) 늘자 순차 검색의 일은 정확히 100배가 됐다. 역색인이 읽은 포스팅도 비슷하게 늘었지만(7.3 → 696.7), 출발점이 훨씬 작다. 시간 차이는 1,000배 가까이 난다.
- 흔한 단어 두 개만으로 된 질문은 15,000편 색인에서도 포스팅 25,880개를 읽는다. 문서 수보다 많다(한 문서에 둘 다 있으면 두 번 센다). 역색인도 흔한 단어 앞에서는 순차 검색과 비슷해진다.

**실패 조건**: 1부에서 두 방법이 찾은 문서 집합이 다르면 `AssertionError`로 멈춘다. 그러면 `build_index()`나 `lookup()`의 구현이 틀린 것이다. `docs/ko/`가 없으면 `FileNotFoundError`다. 저장소 맨 위 폴더에서 실행했는지 확인한다.

**짚어 둘 점**: 이 저장소의 `bm25.py`는 역색인을 쓰지 않는다. `BM25.scores()`는 15편을 모두 돌며 점수를 매긴다. 임베딩 검색(`searcher.doc_vectors @ query`)도 15편 전부와 곱한다. 15편이면 그래도 0.01ms 수준이라 [측정, D장] 색인을 만들 이유가 없다. 문서가 많아지면 이 두 줄이 가장 먼저 바뀐다. 역색인 버전은 G장 종합 실습에서 직접 만든다.

## ⑨ 한계와 실무적 타협

- **교과서**: 문서가 늘면 색인을 만든다. **실무**: 문서 수와 질문 수, 지연 시간 목표를 보고 정한다. 수천 편, 질문 몇 개라면 순차 검색이 더 단순하고 버그도 적다. 실제 검색 서비스는 Lucene 계열(Elasticsearch, OpenSearch)처럼 역색인을 이미 구현한 엔진을 쓴다.
- **교과서**: RAG면 모델이 문서를 근거로 답한다. **실무**: 모델은 여전히 파라미터의 기억을 쓴다. 넣은 문서와 기억이 섞인 답이 나올 수 있다(E장에서 실제 사례를 본다).
- **관련성은 사람의 판단이다.** 정답표를 누가 어떻게 만들었는지가 평가의 한계를 정한다. 이 저장소의 정답표는 질문 하나에 정답 문서 하나만 정해 두었다(F장).

## ⑩ 이해도 점검

**개념**

**결과 예측**
