# G. 종합 실습, 전체 데이터 흐름, 다음에 배울 것

> 라이브러리 없이 검색기를 처음부터 만들고, 그것이 왜 틀리는지 스스로 찾아낸 다음, 실제 문제에 맞는 기술을 골라 본다. 이 장을 막힘없이 끝낼 수 있다면 「RAG는 검색해서 붙이는 것」보다 한참 깊이 이해한 것이다.

이 장은 네 부분이다.

1. [직접 만들기](#1부-직접-만들기): 역색인 + BM25 + 평가기 (코드)
2. [분석과 판단](#2부-분석과-판단): 오답의 원인 찾기, 100배 규모, 디버깅 순서, 기술 고르기 (글)
3. [전체 RAG 파이프라인의 데이터 흐름](#3부-전체-rag-파이프라인의-데이터-흐름)
4. [다음에 배울 것과 우선순위](#4부-다음에-배울-것과-우선순위)

표시 규칙: **[측정]** 은 이 저장소에서 돌려 얻은 값, **[예시]** 는 설명용 값, **[기존 측정]** 은 앞선 장에 기록된 값이다.

## ① 학습 목표

- A~F장의 개념(역색인, 토큰화, IDF, BM25, 평가 지표)을 빈 파일에서 다시 구현한다.
- 자기가 만든 검색기의 오답을 토큰별 점수로 분해해 근본 원인을 찾는다.
- 질문의 성격과 제약을 보고 검색 방법(BM25, 임베딩, Hybrid, 재순위화)을 근거를 들어 고른다.
- RAG 파이프라인의 각 단계에서 데이터가 어떤 모양(문자열, 사전, 배열)으로 바뀌는지 말한다.

## ② 선수 지식

[A](A-before-rag.md), [B](B-lexical.md), [F](F-evaluation.md)장은 필수다. 2부의 판단 문제는 [C](C-vectors.md), [D](D-retrieval.md), [E](E-grounding.md)장도 쓴다.

**처음 상태(아무것도 안 채움)의 예상 결과 [측정]**

```text
[1] tokenize

아직 채우지 않았다: TODO 1: tokenize
```

종료 코드는 1이다. TODO를 하나씩 채우면 검사가 한 칸씩 앞으로 간다.

**다 채웠을 때의 예상 결과 [측정, 참고 답안으로 돌린 출력]**

```text
[1] tokenize
    통과
[2] build_index
    통과: 서로 다른 토큰 903개, 글 길이 합 1380
[3] search
    [('03-firewalls.md', 13.28), ('15-vpns.md', 9.19)]
    통과: bm25.py와 같은 점수
[4] evaluate
    ko: Hit@1 14/15, Recall@3 1.000, MRR@5 0.967
      틀린 질문: 돈으로 살 수 있는 양이 시간이 갈수록 줄어드는 이유는?  기대 12-inflation.md  결과 ['04-compound-interest.md', '12-inflation.md', '03-firewalls.md']
    en: Hit@1 12/15, Recall@3 0.867, MRR@5 0.839
      틀린 질문: Why does it rain?  기대 02-water-cycle.md  결과 ['15-vpns.md', '13-noise-cancelling-headphones.md', '06-dns.md']
      틀린 질문: Why does the ocean rise and fall twice a day?  기대 09-ocean-tides.md  결과 ['15-vpns.md', '10-http-vs-https.md', '09-ocean-tides.md']
      틀린 질문: Why does money buy less over time?  기대 12-inflation.md  결과 ['15-vpns.md', '11-four-stroke-engine.md', '04-compound-interest.md']
    통과

다 통과했다. 이제 guide/G-capstone.md의 2부(분석 질문)로 넘어가자.
```

**결과 해석**: [3]의 13.28과 9.19는 [D장](D-retrieval.md#64-min-max-정규화)의 실제 ko Q3 표에서 `bm25.py`가 낸 점수와 같다. 저장소의 BM25를 역색인 버전으로 다시 만든 것이다. [4]의 숫자는 `labs/score_fusion.py`의 「BM25만」 줄과 같다. 다만 en의 MRR은 거기서는 15등까지 봐서 0.843이고, 여기서는 5등까지만 봐서 0.839다(15등에 있던 Q2를 0점으로 센다).

**실패 조건과 흔한 실수**

| 증상 | 원인 |
| --- | --- |
| [1]에서 `vp`, `pn`이 없다 | 소문자로 바꾸지 않았다 (`VPN` → `vpn`) |
| [1]에서 `a`나 `가`가 사라진다 | 한 글자 단어를 버렸다. `range(max(1, len(word) - 1))` |
| [2]에서 `{'03-firewalls.md': 3}`이 아니다 | tf 대신 1을 넣었거나, 문서 길이를 글자 수로 셌다 |
| [3]의 점수가 조금 다르다 | 평균 길이를 토큰이 아니라 글자로 셌거나, 질문의 중복 토큰을 한 번만 더했다 |
| [4]의 MRR이 다르다 | 5등 밖의 정답을 0이 아니라 1/순위로 셌다 |

## 2부. 분석과 판단

코드를 다 채웠다면 아래 질문에 글로 답한다. 해설은 [answers/G.md](answers/G.md)에 있다.

### 문제 1. 영어 오답은 왜 모두 VPN인가

영어에서 틀린 세 질문의 1등이 모두 `15-vpns.md`다. 질문 주제(비, 밀물, 돈)와 상관없는 문서다.

1. 「Why does it rain?」에 대해, VPN 글과 물의 순환 글이 받은 점수를 **토큰별로** 나눠 출력하는 함수를 만들어라. (`search()` 안의 덧셈을 토큰별로 기록하면 된다.)
2. VPN 글이 이긴 결정적인 토큰은 무엇이고, 그 토큰의 df와 IDF는 얼마인가? 그 토큰은 어느 낱말에서 왔나?
3. 물의 순환 영어 원문을 읽어라. 질문의 핵심 낱말이 문서에 있나?
4. 「불용어(why, does, it …)를 빼면 고쳐진다」는 가설을 세우고 실험하라. 결과는? 그 결과가 근본 원인에 대해 무엇을 말해 주나?
5. 이 질문을 임베딩(dense)과 hybrid는 맞혔다(en dense 1등, hybrid 1등 [측정, D장 6.7]). 왜 그쪽은 가능했나?

### 문제 2. 데이터가 100배가 되면

문서가 15편에서 1,500편이 되었다. 1부의 코드 기준으로 답하라.

1. `build_index()`는 언제 다시 돌려야 하나? 문서 한 편만 추가돼도 모든 문서의 BM25 점수가 바뀌는 이유는?
2. `search()`의 일의 양은 무엇에 비례하나? 「그 질문의 토큰들이 가진 포스팅 길이의 합」을 늘리는 질문은 어떤 질문인가?
3. 지금 정답표 15문항으로 1,500편 코퍼스의 품질을 잴 수 있나? 무엇이 필요한가?

### 문제 3. 검색이 틀렸을 때 어디부터 보나

사용자 신고: 「"방화벽이 뭘 막아요?"라고 물었더니 VPN이 암호화한다는 엉뚱한 답이 왔어요.」 [E장 6.8](E-grounding.md#68-검색-실패와-생성-실패를-구별하는-방법)의 순서를 이 신고에 적용해, 실제로 칠 명령(`retrieve.py`, `answer.py`의 옵션)과 각 단계에서 무엇을 보고 다음으로 넘어갈지 적어라.

### 문제 4. 기술 고르기

아래 상황마다 검색 방법을 고르고, 그 방법이 **실패할 곳**과 그걸 어떻게 잴지까지 적어라. 정답은 하나가 아니다. 근거가 중요하다.

| | 상황 |
| --- | --- |
| (가) | 사내 장애 대응 위키 3,000쪽. 질문은 대부분 오류 코드(`ERR_CONN_RESET`, `E1042`)나 설정 키 이름을 포함한다 |
| (나) | 쇼핑몰 고객 FAQ 200개. 같은 질문을 고객마다 전혀 다른 말로 한다(「환불 언제 돼요」, 「돈 언제 돌려받나요」) |
| (다) | 법률 문서 수만 건, 문서당 수십 쪽. 답이 여러 조항에 흩어져 있고, 틀린 답의 비용이 크다 |
| (라) | 웹에서 모은 블로그 글을 검색하고, 생성 모델이 사용자 대신 메일을 보낼 수 있다 |

### 문제 5. 코드 없이

1부의 파일을 지우고 빈 파일에서 다시 짜 보라. 30분 안에 [3]까지 통과하면 BM25를 「읽을 줄 아는」 게 아니라 「설계할 줄 아는」 것이다. 그다음에는 같은 방식으로 `vectors.py`의 `cosine()`과 `fusion.py`의 `rrf()`도 빈 파일에서 짜 보자.

## 3부. 전체 RAG 파이프라인의 데이터 흐름

`answer.py "허가되지 않은 네트워크 통신을 무엇이 막나?"`(기본값: `--method rerank`, `--k 3`, `--lang ko`)를 실행했을 때, 데이터가 어떤 모양으로 바뀌는지 따라간다. 괄호 안은 그 일을 하는 코드다.

```text
[미리 한 번]  ───────────────────────────────────────────────────────────────────
docs/ko/*.md (파일 15개)
  │ load_chunks(), parse_doc()                                  A장
  ▼
chunks: list[dict] 15개 {file, title, text, body}
  ├─ BM25(texts)  → 문서마다 Counter(두 글자 조각 → tf), 길이, idf 사전     B장
  └─ load_doc_vectors() → doc_vectors: float32 배열 (15, 384), 길이 1     C장
       └─ .cache/embeddings-ko.npz (지문 SHA-256이 같으면 다시 쓰고, 다르면 다시 계산)  7장

[질문마다]  ─────────────────────────────────────────────────────────────────────
question: str
  │ embedder.encode([q], normalize_embeddings=True)
  │   토큰화 → 표에서 꺼내기 → 12층 → 평균 → 길이 1                       C장 6.7
  ▼
query: (384,)
  ├─ dense   = doc_vectors @ query          → (15,) 코사인                C장 6.5
  └─ lexical = bm25.scores(question)        → (15,) BM25 점수             B장 6.6
  │ hybrid(): 0.7 × minmax(dense) + 0.3 × minmax(lexical)                D장 6.4
  ▼
base: (15,)
  │ rerank(): 상위 5편(RERANK_POOL) → (질문, 글) 쌍 5개 → cross-encoder     D장 6.8
  ▼
scores: (5,) → 위에서 k=3편
  ▼
hits: list[(chunk, score)] 3개                        ← 여기까지가 Retrieval
  │ build_prompt(): INSTRUCTION + "[1] 제목\n본문" × 3 + "질문: ..."        E장 6.2
  ▼
prompt: str 하나                                       ← Augmentation
  │ generate(): OpenAI 형식 API → gpt-6-luna
  ▼
answer: str  "방화벽이 … 차단합니다. [1]"                ← Generation

[평가]  ─────────────────────────────────────────────────────────────────────────
data/answer_key.json (질문 15개 × 기대 파일)
  ├─ retrieve.py --check        → Hit@1, 15/15가 아니면 종료 코드 1        F장
  ├─ labs/evaluate.py           → Hit@1, Recall@3/5, MRR@5                4장
  └─ labs/unanswerable.py       → 답 없는 질문의 점수, 생성 모델의 거절      6장
```

**각 화살표에서 틀릴 수 있는 것**

| 화살표 | 틀리는 모양 | 어떻게 알아채나 |
| --- | --- | --- |
| 파일 → 청크 | 답 문장이 다른 청크로 갈라짐, 너무 큰 청크 | 5장의 지표, 청크를 직접 읽기 |
| 청크 → 임베딩 | 128조각 넘어 뒷부분이 잘림 | C장 6.12, 토큰 수 세기 |
| 질문 → 점수 | 옆 주제(dense), 우연한 글자 일치(BM25) | `--method`별로 비교, 토큰별 점수 분해 |
| 점수 → 섞기 | 자가 안 맞음, 튀는 값 | D장 6.3의 분포 확인 |
| 후보 → 재순위화 | 정답이 후보 K편 밖 | Recall@K |
| 상위 k → 프롬프트 | 반쯤 맞는 글, 주입된 지시 | `--show-prompt` |
| 프롬프트 → 답 | 기억으로 답함, 근거 없는 인용, 지나친 거절 | E장의 근거 검사, 사람이 읽기 |

## 4부. 다음에 배울 것과 우선순위

이 교재가 다루지 않았거나 얕게만 다룬 주제다. 우선순위는 「이 저장소의 다음 결정을 얼마나 바꾸는가」로 매겼다.

| 순위 | 주제 | 왜 다음인가 | 시작점 |
| --- | --- | --- | --- |
| 1 | **더 큰 평가 데이터와 개발/시험 분리** | 지금 모든 결론(hybrid > dense, 0.7, rerank)이 15문항이라 흔들린다(F장 6.5). 이게 없으면 아래 무엇을 해도 나아졌는지 알 수 없다 | [allganize/RAG-Evaluation-Dataset-KO](https://huggingface.co/datasets/allganize/RAG-Evaluation-Dataset-KO) (study.md에서 이미 다음 후보로 꼽았다) |
| 2 | **생성 답변 평가 자동화** | 지금은 낱말 규칙으로 거절을 판정해 틀린다(6장). 근거성(groundedness)을 LLM 판정이나 NLI로 재고, 사람 판정과 일치율을 잰다 | E장 6.6의 표 |
| 3 | **실제 긴 문서의 청킹** | 15편은 한 문단씩이라 청킹을 흉내만 냈다(5장). PDF, 표, 제목 구조가 있는 문서에서 다시 잰다 | 5장, 1번의 데이터셋(PDF 포함) |
| 4 | **한국어 형태소 분석 BM25** | 두 글자 조각의 우연한 일치(「수록」)를 형태소 분석으로 줄일 수 있는지 잰다 | B장 6.8 |
| 5 | **질문 다듬기** | 짧고 모호한 질문(「Why does it rain?」)을 검색 전에 고쳐 쓰거나 여러 개로 늘리는 방법 | 「query rewriting」, 「multi-query」, 「HyDE」 |
| 6 | **더 나은 임베딩 모델과 Fine-tuning** | 이 모델은 바꿔 말하기용이고 128조각이 한도다(C장). 질문-답용 다국어 모델과 비교하고, 그래도 부족하면 내 데이터로 Fine-tuning | C장 6.9~6.10 |
| 7 | **ANN과 벡터 DB 실물** | 문서가 수십만을 넘으면 필요해진다. FAISS(IVF, HNSW)로 D장 6.12를 실제 임베딩에 다시 해 본다 | D장 6.11~6.12 |
| 8 | **트랜스포머 내부** | 어텐션의 Q·K·V 행렬, 여러 헤드, 학습 과정. 검색을 쓰는 데는 지금 깊이로 충분하고, 모델을 고치거나 학습시킬 때 필요하다 | C장 6.7 ③ |
| 9 | **도구를 쓰는 생성 모델의 보안** | 지금 RAG는 답만 쓴다. 메일·결제 같은 도구가 붙는 순간 주입 공격(E장 6.7)의 피해가 커진다 | E장 6.7 |

1번이 맨 위인 이유를 한 번 더 적는다. **측정할 수 없으면 개선했는지 알 수 없다.** 2~9번의 어떤 기법을 넣어도, 15문항으로는 한두 문항 차이밖에 볼 수 없고 그 차이는 우연과 구분되지 않는다.
